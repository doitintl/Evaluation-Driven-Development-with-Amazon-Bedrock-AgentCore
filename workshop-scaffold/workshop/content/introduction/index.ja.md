**3.5 〜 4.5 時間で、リグレッションが起きたときにそれを知らせ、具体的に何が壊れたのかを教えてくれるエージェントを構築します。**

始める準備はできましたか。**[モジュール 0: セットアップ](../00-setup/)** に直接進んでください。以下はすべて背景情報です。今読んでも、後で戻ってきても構いません。

:::alert{type="info" header="対象読者と必要なもの (任意の読み物)"}
このワークショップを最も活用できるのは、AWS 上で AI エージェントを構築し (言語もフレームワークも任意)、ローンチ時だけでなくローンチ後の品質にも責任を持ち、「エージェントがリグレッションしたかどうかをどう知るか」に対する AWS ネイティブな答えを求めている **アプリケーション開発者または ML エンジニア** です。

**終了時には、次のことができるようになります。**

1. あらゆるエージェントを AgentCore Observability と Online Evaluation に接続する (マネージドな AgentCore Runtime 上の Strands、または OpenInference アダプター経由の任意のフレームワーク)。これにより、すべての呼び出しが自動的にトレースされ採点される。
2. 評価駆動開発を適用し、推測ではなく評価スコアに基づいてモデル差し替え、プロンプト変更、ツール追加を進める。
3. 既製のコーディングエージェント Power によって EDD をチーム全体に広げ、新しいエージェントすべてが接続方法を継承するようにする。

**前提条件:** TypeScript または Python の基本的な知識 (題材は TypeScript です。Strands のパスは Python を使います)、AWS CLI の操作と CloudFormation テンプレートを読むことへの慣れ、モダンなブラウザ。ローカルへのインストールは不要で、AgentCore や LLM ジャッジの事前知識も不要です。
:::

## EDD が必要な理由

LLM を使った機能をリリースした経験があれば、次のような場面に出会ったことがあるはずです。

- 「このワークロードには別のモデルを検討すべきか」と問われ、答えが推測だった。
- 「あるバグを直すためにプロンプトを変えた。他のものを壊していないか」これも推測だった。
- 「エージェントが制約を無視した」という苦情が来たが、再現できない。

これらは LLM の問題ではなく評価の問題です。**評価駆動開発 (EDD)** は、TDD がコードの正しさを扱うのと同じやり方でエージェントの品質を扱います。振る舞いの変更はすべて「良い」という固定された基準に対して測定され、その基準は変更 *より前* に存在します。

## 2 つのレンズのモデル

このワークショップでは、相補的な 2 つの評価レンズを接続します。それぞれ異なる種類のバグを捉えます。

| | コンテンツのリグレッションを捉える (一貫性のない回答、ハルシネーション) | トラジェクトリのリグレッションを捉える (チェックの省略、順序の誤り) |
|---|:---:|:---:|
| AgentCore Online Eval (LLM-as-Judge、本番トラフィック、100% サンプリング) | はい、これが役割です | いいえ、ジャッジは最終応答しか見ません |
| TS LLM ジャッジのフレームワーク評価 (`travel-agent/eval/` のキュレーションされたケースと expected_trajectory) | 部分的に。ジャッジはケースの提示方法に影響され得ます | はい、これが役割です |

それぞれのレンズは、もう一方のテストで失敗します。

- Nova Lite への差し替えは、LLM ジャッジでは *より高い* スコアになる一方、`plan_route` の前の `query_sites` 呼び出しを省いてモックデータで運良く当たったために、トラジェクトリでは *より低い* スコアになることがあります。
- *正しい* トラジェクトリをたどりながら *一貫性のない* 旅程を生成するモデルは、トラジェクトリを通過してコンテンツで失敗します。

本番環境では、見えないのはトラジェクトリのリグレッションのほうです。ユーザーは、エージェントが制約チェックを省いたことに気づきません。データが変わり、お客様が月曜に Grand Museum に送られる日が来るまでは (月曜は休館です)。

## これが TDD より難しい理由

TDD には決定性という味方があります。同じ入力なら、毎回同じ出力です。エージェントは違います。分散を抑えるための評価の工夫が 2 つあります。

1. **`in_order` セマンティクスによるトラジェクトリ一致**: 実際のツール呼び出しには追加があってもよいものの、期待されるものは順番どおりに現れなければなりません。経路は文章よりはるかに安定しています。
2. **数値ルーブリックによる LLM-as-Judge**: ルーブリックをコード内で固定し、エージェントを差し替えてスコアを比較します。ジャッジは測定器です。安易に変更するものではありません。

## これから扱うアーキテクチャ

![題材: Coordinator にプロンプトを送ります。Coordinator は 3 つの決定的なツールのどれを呼ぶかを選ぶ LLM です。各ステップは CloudWatch にスパンを出力し、GenAI Observability が結果のトラジェクトリを表示します。](/static/images/diagrams/architecture-overview.png)

Coordinator とその 3 つのツールは、開始前からすでに動作しています。これらを変更し、両方のレンズがどう反応するかを観察します。

残りのワークショップがこの 2 点に依存しているため、注目してください。

- **エージェントは Coordinator だけです。** `query_sites`、`plan_route`、`suggest_dining` は固定データに対する単なる関数です。判断を行わないからこそ、Coordinator の選択が評価に値します。
- **すべてのステップがスパンを出力します。** その軌跡がトラジェクトリであり、後からジャッジが「回答は見栄えが良いか」だけでなく「計画の前に制約を確認したか」と問えるようになる唯一の理由です。

ローカルの 2 つ目の評価スイートも実行します。`travel-agent/eval/` には、期待されるツール順序と採点ルーブリックを備えた手書きのテストケースが入っています。何かをデプロイする前に、`npm run eval` で任意のタイミングで実行します。これがデプロイ前の高速なゲートで、AgentCore Online Evaluation がデプロイ後の継続的なゲートです。モジュール 3 では両方を併用します。

準備ができたら: **[モジュール 0: セットアップ](../00-setup/)**。
