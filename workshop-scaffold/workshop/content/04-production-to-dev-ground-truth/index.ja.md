## 課題

`eval/cases.ts` の 6 ケースはローンチ時に、開発者の想定から書かれました。本番のトラフィックはその先に進んでいます。複数都市の質問、アクセシビリティの要件、予算の制約、誰も予期しなかった組み合わせです。モジュール 2 の Online Eval はそうしたセッションを採点しているので、低いスコアがグラウンドトゥルースの古びた箇所をすでに教えてくれています。ログを読んでケースを手書きするやり方はスケールしません。

:::alert{type="success" header="持ち帰るべき 1 つの考え: 低スコアのセッションは、まだ書いていないテストケースである"}
本番の失敗を自動的に `eval/cases.ts` へ移せば、スイートはローンチ当日の推測ではなく実際のユーザー挙動を追いかけます。追加したケースはどれも、その失敗の再発を止めます。
:::

## やること

1. **本番のトラジェクトリを引き出す**: 評価用ロググループに問い合わせ、低スコアのセッションと、ケースが取りこぼしているパターンを見つける。
2. **配線の Power を適用する**: コーディングエージェントに、新しい専門ツールを Coordinator の OTEL 計測へ接続させる。
3. **本番データをテストケースに変換する**: それらのセッションを `Case` オブジェクトに変える。
4. **ループを閉じる**: 拡張した集合で `npm run eval` を実行し、エージェントが新しいパターンを扱えることを確認する。

## ループ

1. **本番のトラフィック** がエージェントに届く。
2. **Online Eval がすべてのセッションを採点する** (モジュール 2)。
3. **低スコアのセッションが抽出される。**
4. **そのパターンがテストケースになる** (このモジュール)。
5. **エージェントが修正され**、それらを扱えるようになる。
6. **デプロイ** し、それ以降そのパターンは守られる。

## ペルソナ

**エージェント型コーディング** のワークフローです。コーディングエージェントがログに問い合わせ、結果をフィルターし、ケースを生成し、新しいツールを配線します。その判断をあなたがレビューします。

## 所要時間

約 60-75 分。コーディングエージェントを使う 2 ページ (4.3 と 4.4) がその大半です。それぞれ数回の権限承認を伴い、4.4 ではフレームワーク評価を 2 〜 3 回実行します。スイート 1 回あたり約 3 分です。
