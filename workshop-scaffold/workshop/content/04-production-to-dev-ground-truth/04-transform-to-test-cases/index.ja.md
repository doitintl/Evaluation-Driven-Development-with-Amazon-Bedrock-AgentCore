ステップ 4.3 は配線を扱いました。このステップでは **ケースファーストの開発ループ** を新しい専門ツールに適用します。**`time_estimator`** で、旅程がユーザーの示した時間の予算に収まるかを確認します。「1 日目は 4 時間しかありません」と言われたら、Coordinator は提案した 1 日目のスケジュールに対して `time_estimator` を呼び、超過するスケジュールの確定を拒否します。

## ステップ 1: Power を読む

Code Editor の **Explorer** で `kiro-powers/edd-driven-agent-dev/POWER.md` を開きます。

その核心のルールはこうです。まず「良い」とはどういうことかを定義すること。次の 3 つがそろうまでエージェントのコードは書きません。

- 制約の範囲をカバーする 5 つのケース。
- LLM ジャッジが使うルーブリック。
- 各ケースの `expected_trajectory`。

:::alert{type="info" header="仕組み: この Power は登録済みの Claude Code skill でもあります"}
ステップ 4.3 と同様、Claude Code 向けにネイティブな skill `edd-driven-agent-dev` として事前登録されているので、自動的に引き込めます。下のパス参照のプロンプトは、どのコーディングエージェントでも動きます。
:::

## ステップ 4: 承認して構築させる

エージェントのコードにゴーサインを出します。次を生み出すはずです。

- `src/agents/time-estimator-agent.ts` (`sites-agent.ts` の形をした TypeBox スキーマ + `AgentTool` ファクトリー)。
- `src/coordinator.ts` の `tools: [...]` 配列への登録行。
- Coordinator のシステムプロンプトの「Your Capabilities」に、`time_estimator` をいつ呼ぶかを述べたエントリ。

最初のビルドの後にユニットテストを実行します。

:::code{language=bash showCopyAction=true showLineNumbers=false}
npm test -- time-estimator
:::

それから、新しいケースと既存の 6 ケースに対してフレームワーク評価を実行します。**`--all` が必須です**。これがないとランナーはコアの 6 ケースだけを読み込み、新しい `time_estimator` のケースは黙って飛ばされるので、すべてが合格して何も学べません。

:::code{language=bash showCopyAction=true showLineNumbers=false}
npm run eval -- --all --output results/time-estimator-first-pass.md
:::

レポートを開きます。**コアの 6 つ、4.2 で `eval/cases.ts` にマージしたもの、そして新しい 5 つ** を見込み、5 ケースあたり数分を確保してください。自分で歩いたときの件数は **15** でした (コア 6 + 本番から掘り出した 4 + time-estimator 5) で、11 ではありません。4.2 のステップ 5 が生成したケースをマージするよう言っており、ステップ 6 のコーディングエージェントがさらに追加するからです。11 より多い件数はループが機能している証拠です。ちょうど 6 の場合は `--all` が新しいファイルを拾っていないので、上のエクスポート名を再確認してください。

:::alert{type="info" header="どの列がゲートで、どれがシグナルか"}
レポートはケースごとに 4 つの判定を与え、そのうち 3 つだけが合否です。

| 列 | 種類 | 意味 |
|---|---|---|
| `Trajectory` | **ゲート** | ツール順序がケースの一致モードを満たしたか |
| `Must contain` | **ゲート** | 必須の文字列が回答にあるか (例: 合計の `330`) |
| `Must not contain` | **ゲート** | 禁止された文字列がないか (例: 超過時の `schedule fits`) |
| `Content` | **シグナル** | ジャッジの 0.0-1.0 のスコアと 1 文の理由 |

トラジェクトリは通常ほぼ即座に緑になります。ツールが登録されればルールを満たすのは簡単だからです。**注意して読む価値があるのは `must_contain` / `must_not_contain` の列** です。回答についてのあなた自身の主張なので、そこでの失敗は曖昧さがなく、ジャッジに依存しません。

コンテンツスコアは、このスキャフォールドでは意図的にゲートに **して** いません。その数値の意味は `eval/judge.ts` が定義しており、しきい値と比べるよりも帯として読むほうがずっと有用です。

| 帯 | ジャッジ自身の定義 |
|---|---|
| 1.0 | ルーブリックを完全に満たし、制約違反なし |
| 0.7-0.9 | 軽微な欠落や表現の問題、制約違反なし |
| 0.4-0.6 | 部分的な充足、または軽度の制約違反 1 件 |
| 0.1-0.3 | 重大な欠落、または明確な制約違反 |
| 0.0 | ルーブリックに対応していない |

つまり 0.30 は「基準をわずかに下回った」ではなく、実際の違反を見たとジャッジが告げているのです。理由の文字列を読んでください。どの違反かが書かれています。
:::

コーディングエージェントに **反復** させてください。失敗した各ケースについて、変更を 1 つだけ提案し (通常はシステムプロンプトの明確化、ときにツールの追加)、再実行し、差分を比較します。

:::alert{type="warning" header="その 1 つの変更が悪化させたら、戻してください。それがこの演習です。"}
これは最も起こりやすいことであり、手法の失敗ではありません。手法が機能しているのです。このページの実際の実行です。

| | `time_estimator_after_route_planning` |
|---|---|
| 最初のパス | コンテンツ **0.55** |
| エージェントの 1 つのプロンプト修正の後 | `--runs 3` で **0.30 / 0.37 / 0.40** |
| 判定 | 安定したリグレッション、ノイズではない |
| とった行動 | **変更を戻した** |
| 戻した後 | 依然として **0.30** |

エージェントの修正は抽象的には妥当でした (所要時間は確認済みの `query_sites`/`plan_route` の出力からのみ取るよう要求する)。それを加えると回答は一貫して悪くなりました。規律に注目してください。行動する *前に* `--runs 3` でリグレッションを確認したので、戻すという判断は 1 つではなく 3 つのサンプルに基づいていました。

そして最後の行が正直な部分です。戻しても 0.55 は返ってきませんでした。あの 1 回の 0.55 は、実際の平均が 0.4 付近にあるケースでの幸運なサンプルだったのでしょう。それが教訓の下にある教訓です。1 回の実行の数値はベースラインではないので、「以前のスコアを取り戻す」は常に達成可能な目標ではありません。できるのは、それ以上悪くするのをやめ、それから繰り返しの実行でそのケースを判断することです。

したがって差分が負のときは:

1. まず `--runs 3` でそのケースを再実行してください。1 つのサンプルでは、リグレッションとジャッジのノイズを区別できません。
2. **STABLE** に悪いなら戻してください。悪い修正の上に 2 つ目の修正を積み重ねないこと。
3. それから、より居心地の悪い問いを立ててください。**ケース** のほうが誤っていないでしょうか。どんな妥当な回答でも満たせないルーブリックは、エージェントではなくグラウンドトゥルースのバグです。曖昧なルーブリックを締めるのは正当な修正であり、赤いケースを緑にするために緩めるのはそうではありません。

正直な 2 度の試みに抗うケースは、赤のまま残して記録する価値があります。既知で理解された赤とともに出荷するほうが、テストを弱めて作り出した緑とともに出荷するより安全です。
:::

## ステップ 5: すべて緑になったら昇格させる

トラジェクトリとコンテンツのスコアがすべてしきい値 (既定のルーブリックでは 0.7 以上) を超えたら、コーディングエージェントは次を行うべきです。

1. `createTimeEstimatorAgentTool()` が `src/coordinator.ts` の `tools` 配列に登録されていることを確認する。
2. システムプロンプトの「Your Capabilities」に、いつ呼ぶかの例とともに `time_estimator` が記載されていることを確認する。
3. スイート全体を再実行し (`npm run eval -- --all`)、新しいケースが改善し、既存の 6 つが劣化していないことを確認する。

Docker のリビルドも、コンテナイメージの入れ替えもありません。Coordinator はプロセス開始時に `time-estimator-agent.ts` をインポートするので、次の `npm start` が新しいツールを取得します。

## ステップ 6: コーディングエージェントを監査する

あなたはいま、skill ファイルの下で動くエージェントにエンジニアリング作業を委任しました。そのパターンを職場で信頼する前に、会話と生成されたファイルを証拠として、このチェックリストで採点してください。

| # | Power のルール | 探すべき証拠 | 合格? |
|---|---|---|---|
| 1 | コードより先にケース | **会話の中で**: `src/agents/time-estimator-agent.ts` がまだ存在しない状態でケースを見せた。これにファイルのタイムスタンプを使わないこと。下の注記を参照 | |
| 2 | レビューのために止まった | 実装に突き進むのではなく、ケースを提案した後に一時停止した | |
| 3 | 妥当なケース設計 | 各ケースが本物の `trajectory_match` モード (`superset`/`in_order`/`exact`/`subset`) を意図的に選び、観測可能な不変条件を持つルーブリックを備えている (「良い」「包括的な」ではない) | |
| 4 | 反復ごとに 1 つの変更 | ケースが失敗したとき、修正を 1 つ提案し、再実行し、比較した。推測的な編集の束ではない | |
| 5 | 結論の前に確認した | ぶれて見える失敗では、1 つのサンプルで勝敗を宣言せず、疑わしいケースを再実行した (`--case <name> --runs N`) | |
| 6 | スイート全体のリグレッション確認 | 最後にすべてのケースを再実行し、既存の 6 つへの副次的被害がないと報告した | |

:::alert{type="warning" header="ルール 1 の証拠はファイルシステムではなく会話の記録です"}
ファイルの日付でルール 1 を決められない理由が 2 つあります。ワークショップのリポジトリのコピーは git のチェックアウトではなくただのディレクトリなので、調べるコミットがありません。そしてルール 4 と 5 は、コードが存在した後に *ケースを見直す* ようエージェントを促すため、ケースのファイルはエージェントのコードより **新しく** なるのが正当です。このウォークスルーでの実測では、`eval/cases-time-estimator.ts` の最終更新が **06:17:13** で、`src/agents/time-estimator-agent.ts` は **05:57:03** でした。最初の評価実行の後に 3 つのルーブリックの改良が入ったという、それだけの理由です。代わりに会話を読んでください。エージェントのファイルが 1 つも存在しない時点で、ケースは画面に出ており、エージェントは承認を待っていました。
:::

正直に採点してください。エージェントが #2 や #5 を飛ばしていたら、Power からそのルールをチャットに貼り戻し、その部分をやり直すよう頼んでください。**skill ファイルは契約であり、このレビューが契約を執行する方法です。** それはご自身の skill も強くします。捉えたすべての違反が skill のテキストのより鋭い MUST になります。本番の失敗をテストケースに変えるフライホイールを、skill 自体に適用するのです。

## 証明したこと

チームはシニアエンジニアをループに入れずに新しい専門ツールを出荷できます。規律 (ケースが先、2 つのレンズ、結論の前に確認、正の差分がなければマージしない) が Power に宿り、その Power に対する人間の監査が誠実さを保つからです。

:::alert{type="success" header="このワークショップの 2 つ目の残る洞察"}
EDD はループが自動化可能だからスケールします。配線は機械的で (ステップ 4.3)、規律は成文化可能です (ステップ 4.4)。合わせれば、EDD は「シニアエンジニアの習慣」から「このコードベースがエージェントを出荷する方法」になります。
:::

## チェックポイント: ループ全体を、あなたの言葉で

走り書きのファイルに 3 行:

1. モジュール 1 が与えたのは ___ (突然何が *見える* ようになったか)。
2. モジュール 2 と 3 はその可視性を ___ に変えた (突然何を *判断できる* ようになったか)。
3. モジュール 4 は ___ によってループを閉じた (本番が動くにつれ、いま何が *自動的に* 改善するか)。

3 行目に「低スコアの本番セッションが新しい評価ケースになる」とあれば、つかんでいます。そのフライホイールが持ち帰るものであり、トラベルエージェントは乗り物にすぎませんでした。
