このワークショップでは、TypeScript 製の旅行プランニングエージェントを題材に、AI エージェントのための **評価駆動開発 (EDD: Evaluation-Driven Development)** を学びます。

これからの 3.5 〜 4.5 時間で、次のことを行います。

1. エージェントを Amazon Bedrock AgentCore Observability に接続し (トレースと構造化ログ)、エージェントの挙動を **可視化する**。
2. すべてのセッションを採点する自動 LLM ジャッジを接続し、品質低下を **検知する**。
3. エージェント内部の推論経路を捉えるトラジェクトリ評価を追加し、どこでリグレッションが起きたかを **特定する**。
4. 本番環境のパターンをテストスイートに取り込み、グラウンドトゥルースを最新に保つことで **ループを閉じる**。

題材は **架空の都市 Luminara のための Coordinator エージェント** です。Coordinator は 3 つの専門ツールをオーケストレーションします。`query_sites` (観光地の検索)、`plan_route` (複数日の旅程プランナー)、`suggest_dining` (レストランの提案) です。旅程には制約があります (Grand Museum は月曜休館、Royal Palace は火曜休館で事前予約が必要、Night Market は金曜から日曜の夜のみ営業、Harbor Cruise は事前予約が必要)。この制約があるため、最終的な回答だけでなくエージェントの *トラジェクトリ* が重要になります。

:::alert{type="info" header="学習: エージェントとは何か、なぜトラジェクトリが重要なのか"}
エージェントは初めてですか。要点は 4 文で説明できます。

通常のプログラムは、あなたが書いたとおりの経路をたどります。**エージェント** は、**ツール** (呼び出してよい関数) のセットを与えられた LLM であり、どれをどの順番で呼ぶか、いつ完了とするかを *自分で* 判断します。ある 1 回の実行で実際に呼び出した順序が、そのエージェントの **トラジェクトリ** です。

その順序を書く人はいないため、完全に予測できる人もいません。同じリクエストでも 2 回の実行で経路が変わることがあり、そして評価を難しくしているのは次の点です。**誤った経路でも、正しく見える回答が出てしまうことがある** のです。営業時間の確認を省いて推測したエージェントは、休館日の博物館に人を送る自信満々の旅程を書けてしまいます。

だからこのワークショップでは、回答だけでなく経路も採点します。最終的なテキストだけを確認していると、問題を知らせてくるのはお客様になります。
:::

## なぜ EDD なのか

推測でエージェントを安定して本番投入することはできません。本番を目指すすべてのエージェントは、4 つの問いに数値で答える必要があります。EDD は 4 つのモジュールを通じて、それらに段階的に答えていきます。

| モジュール | 答える問い | EDD による答え方 |
|---|---|---|
| 1. エージェントの可観測性 | *何が起きたのか* | OTEL トレース + 構造化ログ |
| 2. 継続的モニタリング | *エージェントは良かったのか* | AgentCore Online Evaluation (LLM-as-Judge) |
| 3. トラジェクトリ評価 | *具体的に何が壊れたのか* | フレームワーク評価: 2 つのレンズのモデル |
| 4. 本番から開発へのグラウンドトゥルース | *そもそも「良い」とはどういう状態か* | 本番データ → 新しいテストケース |

このワークショップの中心は 3 番目の問いです。「良いかどうか」という単一のスコアは *何が* 劣化したのかを隠してしまうため、EDD はすべての実行を **2 つの独立したレンズ** で採点します。

- **コンテンツのレンズ** (LLM-as-Judge): 最終的な回答は正確で役に立ったか。
- **トラジェクトリのレンズ** (ツール呼び出しマッチャー): エージェントはそこに至る正しい経路をたどったか。

エージェントは一方のレンズを通過しつつ、もう一方で失敗し得ます。必須の制約チェックを省いて作られた完璧に見える旅程、あるいは正しいツール順序で一貫性のない回答が出るケースです。両方の失敗モードを捉えるには両方のレンズが必要で、モジュールごとに順を追って構築していきます。

## すでにデプロイされているもの

ワークショップを開始した時点で、[AWS CloudFormation](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/Welcome.html) (テンプレートファイルからリソースを作成する AWS サービス) が構築したのは **ブートストラップ** のインフラのみです。

- **Code Editor EC2**: ブラウザ上の VS Code。`travel-agent/` (pi-mono TS) と `travel-agent-strands/` (Strands Python) のリポジトリがクローン済みで、依存関係もインストール済みです。
- Code Editor 用の **VPC + サブネット**。

**AgentCore の Observability + Evaluation インフラは事前デプロイされていません**。モジュール 1 と 2 のなかで、ご自身でデプロイします。

Code Editor の URL は、Workshop Studio の左ナビゲーションにある **Event dashboard** にあります。ここにスタックの出力が直接一覧表示されます。

## これから構築するもの

| モジュール | 所要時間 | ペルソナ | やること | 「なるほど」ポイント |
|---|---|---|---|---|
| 0. セットアップ | 10 分 | 全員 | エージェントを実行し、Luminara に関する質問に答えることを確認する | 「エージェントは動く。次は接続だ」 |
| 1. エージェントの可観測性 | 20-45 分 | 全員 | Path A (Strands) または Path B (任意のフレームワーク) を選び、可観測性の CFN をデプロイし、OTEL を接続してトレースを確認する | 「すべてのツール呼び出しと応答が見える」 |
| 2. 継続的モニタリング | 25 分 | DevOps | 評価器をデプロイし、トラフィックを生成し、ダッシュボードでスコアを確認する | 「品質低下が自動でわかる」 |
| 3. トラジェクトリ評価 | 90-110 分 | 開発者 | 2 つのレンズで採点するモデル差し替えとプロンプト変更の実験、そして自作マッチャーをオンライン評価器としてデプロイ | 「トラジェクトリはコンテンツジャッジが見落とすものを捉える」 |
| 4. グラウンドトゥルースのループ | 60-75 分 | エージェント型コーディング | 本番データを取得し、新しいツールを接続し、実トラフィックからテストケースを生成する | 「本番が開発に情報を与え、開発が本番を改善する」 |

モジュール 3 が長いのは、ページ 3.4 で実際の Online Evaluation の結果を待つためです。20-25 分の待ち時間 2 回を 1 回にまとめる方法は、そのインデックスページで説明します。

## 学習目標

このワークショップを終えると、次のことができるようになります。

1. あらゆる AI エージェント (マネージドな AgentCore Runtime 上の Strands、または OpenInference アダプター経由の任意のフレームワーク) を Amazon Bedrock AgentCore Observability に **接続し**、すべての呼び出しが構造化トレースとレコードを生成するようにする。
2. `Builtin.Helpfulness` またはドメイン固有のルーブリックを持つカスタム LLM-as-Judge を使って、そのトラフィックを AgentCore Online Evaluation で継続的に **モニタリングする**。
3. デプロイ前のフレームワーク評価とデプロイ後の Online Eval の両方を使い、モデル差し替えとプロンプト変更をトラジェクトリを考慮して **評価する**。
4. コーディングエージェントの Power を使って本番のパターンをテストスイートに取り込み、トラフィックの変化に応じてグラウンドトゥルースを最新に保ち、**ループを閉じる**。

## 学習成果

ワークショップ完了後、次のものが手元に残ります。

- AgentCore 互換のトレースとログレコードを出力する、動作する Coordinator エージェント。
- 自動採点を備えた、デプロイ済みの eval+obs CloudFormation スタック。
- 同一エージェントに対して 2 つの評価レンズ (LLM ジャッジ対トラジェクトリ一致) を比較した実践経験。
- 手書きの評価スイートを補完する、本番由来のテストケース。
- EDD の進行に関する明確なメンタルモデル: 観測 → モニタリング → 評価 → グラウンドトゥルース。

## 対象読者

- Amazon Bedrock 上でエージェント型システムを構築する AI / ML エンジニア。
- LLM を利用した機能を本番サービスに統合するアプリケーションエンジニア。
- モニタリングと評価のインフラを担当する DevOps / プラットフォームエンジニア。
- 評価の規律と CI ゲートを担当するデベロッパーエクスペリエンスエンジニア。

本番に近いサービスを 1 つ以上リリースした経験があり、TypeScript または Python を読むことに抵抗がなければ、このワークショップは適しています。AgentCore の経験は **不要** です。

## 前提条件

- TypeScript または Python の基本的な知識 (コードを読み、設定を編集します。新しいエージェントをゼロから書くことはありません)。
- AWS CLI の基本操作 (`aws cloudformation deploy`、`aws logs filter-log-events`)。
- AWS 主催イベントへの招待と Workshop Studio のサンドボックスアカウント。下記の [このワークショップの実施方法](#how-to-run-this-workshop) を参照してください。
- AgentCore の事前知識は不要です。
